🌊 We are excited to announce the official release of **Apache Fluss 1.0**!

This is the first release since Fluss [graduated to a Top-Level Project](/blog/apache-fluss-graduates-to-top-level-project/), and the first to drop the `incubating` suffix. It is also the largest release the project has shipped: 812 commits from 81 contributors over roughly six months.

1.0 is a release about running Fluss in production. The coordinator is no longer a single point of failure, primary-key tables can fail over quickly, a cluster under pressure pushes back instead of falling over, and Apache Hudi joins the set of lakehouse formats Fluss can tier into. Alongside that, filter pushdown now runs all the way down at the server, and both the Flink and Spark connectors close long-standing gaps.

## Release Highlights

### Filter and predicate pushdown, end to end

Filter pushdown lets a scan carry a predicate to the server rather than filtering after the rows arrive. Underneath, a new log batch format carries per-batch statistics, so the server can skip whole record batches that cannot match instead of decoding and shipping them.

Nothing changes in your queries. A `WHERE` clause in Flink or Spark is translated into a Fluss predicate and evaluated at the server:

```sql
-- The predicate is pushed into Fluss; batches that cannot match are never read.
SELECT order_id, total_amount
FROM orders
WHERE shop_id = 10000 AND total_amount > 500;
```

The same capability is available directly on the Java client through `Scan#filter(Predicate)`, so applications that read Fluss without a query engine get it too. Iceberg scans also became more selective, reading column statistics only when a scan filter is actually present.

### Coordinator high availability

Coordinator high availability is now supported: standby coordinators elect a leader among themselves and promote a standby when the active one fails. That keeps cluster metadata requests, rebalancing, and recovery of data from downed tablet servers available through a coordinator failure, where before a cluster ran a single CoordinatorServer and losing it stalled all of that until an operator brought it back.

There is no new option to turn on. Start more than one CoordinatorServer against the same ZooKeeper ensemble and they register themselves, elect a leader, and keep the rest as standbys:

```yaml title="server.yaml (coordinator 1)"
bind.listeners: FLUSS://192.168.10.100:9123
zookeeper.address: 192.168.10.199:2181
zookeeper.path.root: /fluss
```

```yaml title="server.yaml (coordinator 2, the standby)"
bind.listeners: FLUSS://192.168.10.101:9123
zookeeper.address: 192.168.10.199:2181
zookeeper.path.root: /fluss
```

Leader election is protected by a coordinator epoch, so a coordinator that was partitioned away cannot come back and act on stale state, and a standby tracks dynamic configuration changes while it waits so it does not take over with an outdated view of the cluster. Requests that must be served by the leader now fail with a dedicated `NotCoordinatorLeaderException` rather than a generic error.

### Standby replicas for primary-key tables

Standby replicas for primary-key tables are now supported. A standby holds recent KV snapshots on another tablet server, so a promoted replica starts from a snapshot it already has instead of rebuilding its RocksDB state from an older snapshot plus a long changelog replay.

The coordinator turns this on for newly created primary-key tables. Tables created before 1.0 are treated as disabled, and can opt in:

```sql
-- Enable standby replicas on an existing primary-key table
ALTER TABLE pk_table SET ('table.kv.standby-replica.enabled' = 'true');
```

### Multi-disk and multi-location storage

Spreading data across multiple directories is now supported, both locally and remotely. A tablet server can put its log, KV and checkpoint files on several local disks instead of one, and a cluster can distribute KV snapshots and remote log files across several remote locations rather than a single bucket or path:

```yaml
# Local: spread log, KV and checkpoint files across several disks
data.dirs: /mnt/disk1/fluss,/mnt/disk2/fluss,/mnt/disk3/fluss

# Remote: distribute KV snapshots and remote log files across locations
remote.data.dirs: s3://bucket-a/fluss,s3://bucket-b/fluss
remote.data.dirs.strategy: WEIGHTED_ROUND_ROBIN
remote.data.dirs.weights: 3,1
```

A location is chosen per table or partition when it is created, using `ROUND_ROBIN` by default or `WEIGHTED_ROUND_ROBIN` when you want to bias placement. The existing single-value `remote.data.dir` still works; when migrating, place it first in the new list.

### Cluster protection and back-pressure

Limits and back-pressure are now applied at the points where a busy or unbalanced cluster previously ran itself out of disk, memory, or coordinator capacity. Instead of failing outright, a server under pressure slows writers down, refuses work it cannot take, and keeps serving:

```yaml
# Stop accepting writes at 85% disk usage, resume once back under 80%
server.data-disk.write-limit-ratio: 0.85
server.data-disk.write-recover-ratio: 0.80

# Throttle writers when RocksDB L0 files pile up, rather than falling behind
kv.backpressure.l0-slowdown-trigger: 8

# Refuse KV leadership this server does not have the memory to serve
kv.leader-replica.memory-reserved: 8mb
tablet-server.advertised-resource.memory-size: 16gb
```

Alongside these, a table lifecycle throttler stops a mass drop from flooding the coordinator queue, KV leader promotion is rejected while a disk write lock is held, and the Netty server and RPC decoder now bound request sizes.

### Flink connector

`DELETE` and `UPDATE` in batch mode are no longer restricted to a full primary-key match. Fluss now implements Flink's row-level delete and update interfaces, so arbitrary predicates work:

```sql
-- Previously only supported with a condition on the full primary key
DELETE FROM pk_table WHERE order_date < '2026-01-01';

UPDATE pk_table SET status = 'archived' WHERE shop_id = 10000;
```

Aggregation tables can now be written exactly once with undo-based recovery, Flink batch reads can run on an SST merge, and the source implements `SupportsWatermarkPushDown`. Lookup joins gained a `lookup.insert-if-not-exists` option, union read is available from the DataStream API, and the AGGREGATION merge engine now accepts partial updates.

This release also fixes a long tail of correctness bugs: partition pruning for non-string partition keys, `COUNT(column)` pushdown over nullable columns, batch queries against an empty lake-enabled table, and checkpointing on the `$changelog` and `$binlog` virtual tables.

### Spark connector

Batch union read across the hot and lake tiers is now supported from Spark, for both log and primary-key tables. Querying a lake-enabled table just works; the connector unions fresh Fluss data with historical lake data behind the scenes:

```sql title="Spark SQL"
-- Reads fresh rows from Fluss and historical rows from the lake, as one table
SELECT SUM(total_price) AS total_revenue FROM fluss_order_with_lake;
```

Structured Streaming reads landed too, and filter, partition and limit pushdown were added across these paths. The connector now builds for Scala 2.13 as well as 2.12.

Spark also gained `MAP` type support, a `scan.maxRecordsPerPartition` option for splitting log-table input partitions, and a `numRowsRead` metric surfaced in the Spark UI.

### Java client

One scanner or writer can now cover many tables instead of one each, through `Connection#getMultiTable()`. A single scanner subscribes to buckets across tables and each record tells you where it came from:

```java
try (MultiTableLogScanner scanner =
        connection.getMultiTable().newMultiTableScan().createLogScanner()) {

    scanner.subscribeFromBeginning(TablePath.of("fluss", "orders"), 0);
    scanner.subscribeFromBeginning(TablePath.of("fluss", "payments"), 0);

    while (running) {
        for (MultiTableRecord record : scanner.poll(Duration.ofSeconds(1))) {
            TablePath table = record.getTablePath();
            ChangeType changeType = record.getChangeType();
            InternalRow row = record.getRow();
            // process row, knowing which table and change type it came from
        }
    }
}
```

This suits fan-in workloads such as a CDC ingestion job feeding many tables, where holding one connection and one writer per table did not scale. Complex types (`ARRAY`, `MAP`, `ROW`) are now supported on the Java API, and the POJO converter handles column aliasing and enum conversion.

Log data can also be scanned straight into Arrow record batches, and a round of allocator work cut how much memory the client holds while doing it.

### Full KV scan for primary-key tables

Full KV scan reads the current state of a primary-key table straight out of the server's RocksDB store, with results streamed back over a new `ScanKv` request. `Scan#createBatchScanner()` now returns the whole table in one call, expanding across every bucket and, for partitioned tables, every partition:

```java
try (BatchScanner scanner = table.newScan().createBatchScanner()) {
    while (true) {
        CloseableIterator<InternalRow> batch = scanner.pollBatch(Duration.ofSeconds(5));
        if (batch == null) {
            break; // end of scan
        }
        try {
            while (batch.hasNext()) {
                InternalRow row = batch.next();
                // process row
            }
        } finally {
            batch.close();
        }
    }
}
```

This makes bulk export and full-snapshot reads practical without a query engine. Scanner lifetime, concurrency and batch size are all bounded by configuration so a large scan cannot monopolise a server.

### Operability

Cluster health can now be queried directly through `Admin#getClusterHealth()` instead of inferred from metrics, and remote storage can be swept for files that no table still references, either through a `remove_orphan_files` Flink action or automatically when a tablet starts up.

Retention and shutdown behaviour also became more predictable, with a TTL for local log segments, periodic checkpointing of log recovery points, and batched leader updates during controlled shutdown.

### Metrics and observability

InfluxDB is now supported as a metrics backend, for both v2 and v3:

```yaml
metrics.reporters: influxdb
metrics.reporter.influxdb.host-url: http://localhost:8181
metrics.reporter.influxdb.bucket: fluss_metrics
metrics.reporter.influxdb.token: your-influxdb-token
metrics.reporter.influxdb.push-interval: 10 SECONDS
```

The Prometheus PushGateway reporter can now authenticate with basic auth. Several new server metrics also landed, covering log start offsets, per-processor request queue depth, per-table bucket and partition counts, and local log physical size per bucket. For lake tiering specifically, new metrics expose the last successful tiering time, pending record lag, and per-table tiering freshness.

### Deployment: Helm chart

The Helm chart now covers what a production Kubernetes deployment needs: SASL authentication (including to ZooKeeper), secrets pulled from existing Kubernetes objects or an external provider, scheduling controls, and the usual pod-level escape hatches such as extra volumes, init containers, annotations, labels and a PodDisruptionBudget.

### Security

Authentication and secret handling both became more workable for real deployments. SASL/PLAIN now supports multiple users defined in cluster properties, and secrets can be resolved from an external provider rather than written into config files:

```yaml
# Several SASL/PLAIN users, defined directly in cluster configuration
security.sasl.plain.credentials: admin:admin-secret,bob:bob-secret

# ...or keep the secret out of the file entirely and resolve it at load time
config.providers: directory
config.providers.directory.param.allowed.paths: /etc/fluss/secrets
datalake.paimon.s3.secret-key: ${directory:/etc/fluss/secrets:s3-secret-key}
```

Sensitive values are redacted from startup logs, and S3 delegation-token access keys are masked. Authorization also covers more operations, including `listOffsets`, `databaseExists` and `tableExists`.

Note that modifying ACLs now requires `ALL` permission on the target resource, which is a breaking change; see the upgrade notes below.

### Apache Hudi as a lakehouse tier

Fluss now supports tiering older data to Apache Hudi, alongside Paimon, Iceberg and Lance. Tiering moves data out to a lakehouse table so it stays queryable long after it ages out of hot storage.

Configure Hudi as the lakehouse storage in `server.yaml`:

```yaml
datalake.enabled: true
datalake.format: hudi

# Hudi catalog configuration, using DFS catalog mode
datalake.hudi.mode: dfs
datalake.hudi.catalog.path: /tmp/hudi
```

Primary-key Fluss tables are written as Hudi Merge-On-Read tables and log tables as Copy-On-Write tables. The integration is complete enough to use end to end: a Hudi lake catalog, writer and committer, compaction inside the tiering service, predicate pushdown, and Flink union read for both log and primary-key tables. See the [Hudi documentation](https://fluss.apache.org/docs/1.0/streaming-lakehouse/datalake-formats/hudi/) for the current limitations.

### Lakehouse tiering

The tiering service itself got steadier this release, independent of which lake format it targets. Temporary files now go somewhere you choose rather than filling `/tmp`, restarts back off exponentially instead of hammering, and the tiering source is no longer chained with the committer.

```shell
${FLINK_HOME}/bin/flink run \
    -Dparallelism.default=3 \
    /path/to/fluss-flink-tiering-1.0.0.jar \
    --fluss.bootstrap.servers localhost:9123 \
    --datalake.format paimon \
    --datalake.paimon.metastore filesystem \
    --datalake.paimon.warehouse /tmp/paimon \
    --lake.tiering.io.tmp.dirs /mnt/disk1/tiering,/mnt/disk2/tiering
```

Paimon gained support for custom table paths and altering lake table properties, and Iceberg gained `ADD COLUMN` schema evolution and partition-spec validation before tiering begins.

### RoaringBitmap SQL functions

RoaringBitmap functions are now available in Flink SQL, registered through `FlussCatalog`. They cover the common distinct-count and set-operation patterns, such as counting unique visitors, without materialising the individual IDs.

Combined with the `rbm32` aggregation merge engine, each window writes a bitmap batch and Fluss unions batches sharing a key, so the cumulative distinct count is maintained in storage:

```sql
USE CATALOG fluss_catalog;

-- Store one cumulative bitmap per page in Fluss.
CREATE TABLE page_uv (
    page_id  BIGINT,
    uv_bitmap BYTES,
    PRIMARY KEY (page_id) NOT ENFORCED
) WITH (
    'table.merge-engine'      = 'aggregation',
    'fields.uv_bitmap.agg'    = 'rbm32'
);

-- Build one bitmap per page every five seconds. Each completed window writes
-- another bitmap batch, and rbm32 unions it into the existing page bitmap.
INSERT INTO page_uv
SELECT page_id,
       rb_build_agg(user_id) AS uv_bitmap
FROM TABLE(
    TUMBLE(
        TABLE click_events,
        DESCRIPTOR(proc_time),
        INTERVAL '5' SECOND
    )
)
GROUP BY page_id, window_start, window_end;

-- Query the UV value on pages
SELECT page_id,
       rb_cardinality(uv_bitmap) AS uv
FROM page_uv
WHERE page_id = 1;
```

The set includes the aggregate functions `rb_build_agg`, `rb_or_agg` and `rb_and_agg`, plus scalar functions for constructing and combining bitmaps. See [SQL Functions](https://fluss.apache.org/docs/1.0/engine-flink/sql-functions/) for the full reference.

### Filesystems

Tencent COS is now supported as a storage backend. Drop `fluss-fs-cos` into `${FLUSS_HOME}/plugins/cos/` and point remote storage at a `cosn://` path:

```yaml title="server.yaml"
remote.data.dir: cosn://<your-bucket>/path/to/remote/storage
fs.cosn.bucket.endpoint_suffix: cos.ap-guangzhou.myqcloud.com
fs.cosn.userinfo.region: ap-guangzhou

# Either direct credentials, or a credentials provider
fs.cosn.credentials.provider: <your-credentials-provider>
```

The S3 and Azure paths also gained more ways to obtain credentials, including the default AWS credential chain and a custom credentials-provider mode, so Fluss can lean on the environment's own identity setup instead of static keys in config.
